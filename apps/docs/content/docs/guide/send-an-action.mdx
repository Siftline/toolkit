title: Send an Action
description: Turn a routed Decision into an HTTP request, then send it.
---

Sending is the one step the CLI does not do. A Decision names an Action by its id, and
`@siftline/actions` sends it:

```bash
npm install @siftline/actions
```

Declare your Actions once with `defineActions`. Each has an id, an Action kind and a config
for that kind. Two Actions may share a kind: tickets can go to one webhook and escalations to
another. Every config is checked against its kind's schema when you define it, so a missing URL
fails at startup rather than on the first Record.

</include>

`dispatch(decision, record, actions, recipe)` sends a routed Decision to the Action it selected.
`record` is the Record the Decision is about, as you know it: `{ text, sender?, source? }`. A
Decision carries only the Record's id, and a Body template may want its text. It builds the
request with that Action's Adapter, sends it once through the global `fetch`, and returns
`{ action, request, response }`. Pass `{ fetch }` to send through another one, such as a test
stub or a Worker's.

Building and sending are still two steps underneath. An Adapter's `build` is pure: the same
Decision, Record, config and Recipe always produce the same bytes. So a preview is `build`
alone, with nothing sent:

## The webhook

Without a Body template, the body is the Decision line itself, with no envelope, so the
receiver runs `parseDecision` on it. With a `secret` the request carries an HMAC-SHA256 of the
body. Every request carries an `Idempotency-Key` of `<decision id>:<action id>`, which is the
key to deduplicate on if the same Decision is ever sent twice:

## Shape the body

A receiver that wants its own JSON, such as a Discord webhook, gets a Body template: the webhook
config's `body`. It MUST be valid JSON. Its string values may hold variables, and nothing else in
it changes:

| Variable             | Value                                                          |
| -------------------- | -------------------------------------------------------------- |
| `{{record.id}}`      | The Decision's `recordId`                                      |
| `{{record.text}}`    | `text` from the Record you pass                                |
| `{{record.sender}}`  | `sender` from the Record you pass, if any                      |
| `{{record.source}}`  | `source` from the Record you pass, if any                      |
| `{{answers.<name>}}` | The answer to that Question: a label, a boolean, a level index |
| `{{decision.id}}`    | The Decision's id                                              |
| `{{recipe.name}}`    | The Recipe's name                                              |
| `{{rule}}`           | The id of the Rule that selected the Action                    |

A string value that is exactly one variable becomes that value with its type:
`"{{answers.wants_human}}"` sends `true`, not `"true"`. A variable inside other text becomes
text, escaped as JSON, so quotes and newlines in a Record's text cannot break the body. An absent
value, such as a `sender` you did not pass, is `null` on its own and nothing inside text. Object
keys are never rendered. There are no filters and no conditions.

`defineActions` rejects a template that is not JSON, a variable outside the table, or a stray
`{{`. It cannot know your Questions, so `build` rejects an `answers.<name>` the Recipe does not
ask, before anything is sent. With a `secret`, the signature covers the rendered body.

## Failures

`dispatch` returns `null` and sends nothing when the Decision went to Review or its Rule
selected no Action. It throws `ActionBuildError` when the Decision names an Action id you did
not define, which is what a stale Rule looks like. `defineActions` throws the same error for an
unknown kind, an invalid config or an invalid Body template, naming the Action id.

A send that does not land throws `ActionFailedError`: a non-2xx status or a `fetch` that
rejects. It carries the `status` and a `retryable` flag that is true for 408, 429, 5xx and
network failures. `dispatch` retries nothing and sets no timeout: pass `{ signal }` for that.

`build` alone throws `ActionBuildError` when the Decision selected no Action, or when a Body
template names a Question the Recipe does not ask. It does not check
`review`; `dispatch` does, because it is the step that sends.
